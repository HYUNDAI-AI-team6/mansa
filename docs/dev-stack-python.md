# Python 개발 가이드
Python 3.11의 문법과 표준 라이브러리를 기준으로 한다.
개발 기준 버전은 Python 3.11.9다. 설치·실행·검사 명령은 README에 기록한다.

## 1. 스택과 개발 도구

### 기본 선택 기준

필요한 기능에 맞춰 라이브러리와 처리 방식을 선택한다.
파일·경로·일반 데이터 처리에는 표준 라이브러리를 사용하고,
추가 라이브러리는 필요한 기능과 목적이 명확할 때 도입한다.

### 구성

아래 구성을 기준으로 필요한 도구만 선택한다.
Python 3.11.9에서 함께 동작하는 패키지를 선택하고 uv로 버전을 관리한다.

| 역할 | 도구 | 적용 기준 |
|---|---|---|
| 모델 호출 | OpenAI SDK, `langchain_openai` | 사용할 호출 방식을 정하고 일관되게 적용 |
| 프롬프트·체인 | `langchain_core`, LCEL | 입력 → 프롬프트 → 모델 → 결과 변환 연결 |
| 구조화 출력 | Pydantic, OutputParser | 결과를 정해진 필드로 받아야 할 때 사용 |
| 문서 검색 | TextSplitter, Chroma, FAISS | 문서를 나누고 관련 내용을 찾아야 할 때 사용 |
| 대화·분기 | 대화 기록, LangGraph | 대화 유지나 상태에 따른 분기가 필요할 때 사용 |
| 화면 | Gradio | 질문 입력과 답변 표시를 빠르게 연결 |
| 검색 개선 | BM25, CrossEncoder | 기본 검색의 실패 사례가 확인됐을 때 검토 |

LCEL은 처리 단계를 이어 붙이는 방식이고, LangGraph는 상태와 분기로 실행 흐름을 구성한다.
단순한 순차 흐름은 체인으로 시작할 수 있고, 여러 경로를 관리해야 하면 그래프를 검토한다.
그래프는 분기를 명시하기 좋지만 상태와 종료 조건을 추가로 관리해야 한다.

`langchain`, `langchain_classic`, `langchain_core`는 사용하는 패키지 버전에 맞춰 import한다.
공식 문서와 실제 실행 결과로 호환성을 확인한다.

| 영역 | 표준 라이브러리 | 용도 |
|---|---|---|
| CLI | `argparse`, `sys` | 인자 해석, 입출력과 종료 코드 처리 |
| 데이터·경로 | `json`, `pathlib` | JSON 처리와 파일시스템 경로 관리 |
| 데이터 모델 | `dataclasses`, `typing` | 데이터 구조와 함수 간 계약 표현 |
| 파일 저장 | `tempfile`, `os` | 임시 파일 생성과 파일 교체 |
| 테스트 | `unittest`, `unittest.mock` | 동작 검증과 외부 의존성 대체 |
| 프로세스 실행 | `subprocess` | 외부 프로그램 실행과 결과 확인 |

### 가상환경과 의존성 관리

uv의 프로젝트 관리 기능을 사용한다.

| 파일·폴더 | 용도 | Git 공유 |
| --- | --- | --- |
| `pyproject.toml` | 필요한 패키지와 Python 지원 범위 | 공유 |
| `uv.lock` | 간접 의존성을 포함한 패키지의 확정 버전 | 공유 |
| `.python-version` | 사용할 Python 버전 `3.11.9` | 공유 |
| `.venv/` | uv가 생성하고 관리하는 가상환경 | 제외 |

코드의 `import`는 각 Python 파일에 작성한다. 표준 라이브러리는 설치 목록에 넣지 않는다.

- 패키지 추가는 `uv add`, 삭제는 `uv remove`를 사용한다.
- 패키지 변경 시 `pyproject.toml`과 `uv.lock`을 함께 반영한다.
- `uv.lock`은 직접 수정하지 않는다. 팀원은 `uv sync --locked`로 확정된 버전을 설치한다.
- 특정 패키지 갱신은 `uv lock --upgrade-package 패키지명`으로 하고 `uv sync --locked` 후 검증한다.
- import 이름과 설치 패키지 이름이 다를 수 있으므로 설치 패키지 이름을 확인한다.
- 전역 환경의 패키지 목록을 그대로 복사하지 않는다.
- 편집기의 Python 실행 환경도 같은 `.venv`를 선택한다.
- 팀에서 사용하는 uv 버전을 README에 기록한다.

처음 프로젝트를 만드는 사람은 uv 설치 후 루트에서 한 번 실행한다.
요청한 Python 버전이 없으면 uv가 다운로드할 수 있다.

```powershell
uv --version
uv init --bare --python 3.11.9
uv python pin 3.11.9
uv sync
```

`pyproject.toml`의 Python 지원 범위는 `>=3.11.9,<3.12`로 맞춘다.
실제 사용할 패키지는 `uv add 패키지명`으로 추가한다. 개발 도구는 `uv add --dev 패키지명`으로 추가한다.

팀원은 저장소를 받은 뒤 아래 명령으로 설치와 Python 버전을 확인한다.

```powershell
uv sync --locked
uv run --locked python --version
```

프로그램과 검사는 `uv run --locked`로 실행한다.
`requirement.txt`를 별도로 관리하거나 `uv pip`로 패키지를 따로 설치하지 않는다.
새 팀원도 위 설치 과정으로 환경을 구성하고 핵심 기능을 실행할 수 있어야 한다.

### 자동 검사 도구를 추가할 때의 두 선택지

| 선택지 | 장점 | 비용·한계 |
|---|---|---|
| `unittest`와 코드 리뷰 | 추가 설치 없이 테스트를 시작할 수 있음 | 스타일·타입 위반은 리뷰에 의존함 |
| 린터·타입 검사기 추가 | 반복되는 스타일·타입 검사를 자동화할 수 있음 | 도구 버전·설정·기존 위반 처리 필요 |

기존 도구가 있다면 그 구성을 우선한다. 새 도구를 도입할 때는 검사부터 수행하고,
자동 수정이나 엄격한 설정 전환은 기존 오류와 호환성 영향을 확인한 뒤 적용한다.
역할이 겹치는 도구를 불필요하게 함께 설치하지 않는다.

## 2. 구조와 의존 방향

- 실행 진입점은 입력 해석과 결과 출력을 연결한다.
- 계산·변환 로직이 CLI나 UI를 직접 호출하지 않도록 한다.
- 데이터 변환 코드가 파일 위치를 찾거나 외부 서비스를 호출하는 책임까지 맡지 않게 한다.
- 외부 데이터 형식은 경계에서 해석하고 내부에서 사용할 형식으로 변환한다.
- 파일 읽기, 데이터 해석, 계산, 파일 저장을 한 함수에 몰아넣지 않는다.
- 책임을 구분하려고 불필요한 클래스 계층이나 프레임워크를 만들지 않는다.

공개 함수와 재노출 import는 사용하지 않는 것처럼 보여도 호출부를 확인한 뒤 변경한다.
모듈 배치를 바꿀 때는 실행 진입점, 설치 방식과 테스트 import를 함께 확인한다.

### LLM 코드의 최소 역할 구분

기능이 있는 경우에만 다음 책임을 구분한다. 각 책임마다 파일을 만들 필요는 없다.

- 설정: 모델명, 데이터 경로, 검색 개수와 환경변수 확인
- 프롬프트: 모델에 전달할 지시와 입력 변수
- 처리: 검색, 모델 호출, 결과 변환과 필요한 도구 실행
- 화면: 사용자 입력, 답변 표시와 오류 안내

팀원이 나눠 작업하는 함수는 인자, 반환값과 실패 조건을 먼저 합의한다.
예를 들어 답변과 출처를 화면에 넘길 때 문자열인지 구조화된 데이터인지 통일한다.
프롬프트의 변수 이름과 체인에 전달하는 데이터의 키도 함께 맞춘다.

## 3. 함수·이름·주석

- 들여쓰기는 공백 4칸을 사용한다.
- 함수·변수·모듈은 `snake_case`, 클래스는 `PascalCase`, 상수는 `UPPER_CASE`로 작성한다.
- 한 줄은 100자 이하를 기준으로 하고 사용하는 포맷터 설정과 맞춘다.
- 함수는 한 가지 처리 단계가 드러나도록 이름을 짓는다.
- 함수는 30줄 이하를 목표로 하되 의미 없는 분리나 여러 문장을 한 줄에 합치는 방식은 피한다.
- 분리한 함수는 이름으로 책임을 설명하고 입력·출력 관계가 명확해야 한다.
- 함수 밖의 가변 상태를 많이 참조하는 중첩 함수는 인자로 의존성을 드러내는 방식을 검토한다.
- 단순 변환은 컴프리헨션, 오류 처리·상태 변경이 있는 흐름은 명시적인 반복문을 쓴다.
- 주석에는 코드로 알기 어려운 이유, 입력 형식의 제약과 호환성 조건을 적는다.

### 함수 설명 주석 규칙

- 구현 코드의 모든 함수와 메서드에 **한국어 docstring**을 작성한다.
  생성자, 데이터 검증 메서드, 내부 보조 함수와 중첩 함수도 포함한다.
- 함수의 역할, 입력의 의미와 적용 조건, 반환값의 의미를 설명한다.
  기본 문법이나 함수 이름을 그대로 풀어 쓴 설명은 반복하지 않는다.
- 중요한 예외와 실패 조건, 입력 변경 여부, 파일 저장·캐시·외부 API 호출 같은
  부수 효과가 있으면 함께 적는다. 필요한 경우 설계를 택한 이유도 설명한다.
- 검증 범위와 구현의 한계를 정확히 적는다. 형식 검사를 의미 검증처럼 표현하거나
  구현하지 않은 동작을 보장한다고 적지 않는다.
- 간단한 함수는 한두 문장으로 설명하고, 복잡한 함수는 필요한 내용을 짧은 단락으로 나눈다.
- 함수 내부의 `#` 주석은 코드만으로 알기 어려운 이유나 주의점을 보충할 때 사용한다.
- 함수 동작을 변경하면 관련 docstring도 함께 갱신한다.
- 주석만 수정하는 작업에서 로직·시그니처·테스트 수집 범위를 함께 변경하지 않는다.
- 테스트 함수, 픽스처와 테스트 보조 함수의 docstring은 필요한 경우에 작성한다.
  기존 테스트 설명 주석을 이 규칙 때문에 삭제하지 않는다.

## 4. 타입과 데이터 모델

### 외부 입력과 내부 데이터를 구분한다

외부 입력에는 누락 필드, 예상과 다른 타입과 알 수 없는 값이 포함될 수 있다.
경계에서 자료형과 필요한 조건을 확인한 뒤 내부에서 사용할 데이터로 변환한다.
타입 주석만으로 외부 입력이 검증됐다고 간주하지 않는다.
Python 런타임은 타입 주석을 자동으로 강제하지 않는다.

- 새 함수와 모듈 간 경계에는 입력·반환 타입을 명시한다.
- 안정된 공통 데이터는 데이터 클래스로 표현할 수 있다.
- 원본 레코드나 가변 구조를 표현하는 `dict`까지 모두 클래스로 바꾸지는 않는다.
- 배열·중첩 객체·문자열이 들어오는 값을 임의로 단순한 타입으로 좁히지 않는다.
- `Any`는 형식을 알 수 없는 경계에 제한하고, 사용 전 필요한 검증을 수행한다.
- 타입을 맞추기 위해 문자열로 강제 변환하거나 정보를 버리지 않는다.
- 기존 코드의 타입 보강은 관련 동작과 호환성을 확인하면서 진행한다.

### 가변 기본값과 객체 소유권

함수 기본값의 빈 리스트·딕셔너리를 호출 간 공유하지 않는다.
데이터 클래스의 가변 필드는 `field(default_factory=...)`를 사용한다.
다음 예제는 객체별로 독립적인 리스트가 만들어지는지 확인한다.

```python
from dataclasses import dataclass, field


@dataclass
class ItemGroup:
    """객체별로 독립적인 항목 목록을 보관한다."""

    items: list[str] = field(default_factory=list)


first = ItemGroup()
second = ItemGroup()
first.items.append("sample")

assert first.items == ["sample"]
assert second.items == []
```

`frozen=True`는 필드 재할당을 제한하지만 내부 리스트까지 불변으로 만들지는 않는다.
불변 모델이 필요하다면 내부 자료구조와 갱신 방식까지 함께 설계한다.

## 5. 예외 처리와 실행 경계

예외를 잡을 위치는 어떤 복구나 보고를 할 수 있는지에 따라 정한다.

| 위치 | 처리 기준 | 이유 |
|---|---|---|
| 내부 변환 함수 | 처리 가능한 구체 예외만 잡거나 호출자에게 전달 | 구현 결함을 정상 결과로 숨기지 않음 |
| 입력 읽기 | 잘못된 입력의 거부·건너뛰기 정책을 명시 | 일부 실패를 전체 성공으로 오해하지 않게 함 |
| CLI·API·UI 경계 | 오류 응답이나 실패 종료 코드로 변환 | 호출자가 성공과 실패를 구분할 수 있게 함 |

- 내부 함수에 `except Exception`을 무조건 확산하지 않는다.
- 실행 경계의 포괄적인 예외 처리는 오류 기록과 실패 전달 목적이 명확해야 한다.
- `except:`로 오류를 삼키거나 실패를 빈 결과로 숨기지 않는다.
- 오류 의미를 바꿔 전달할 때는 `raise ... from ...`으로 원인 예외를 보존한다.
- 외부 API에는 timeout을 두고 재시도 가능한 오류에만 제한된 재시도를 적용한다.
- 오류 보고에 인증 정보, 개인 정보와 입력 전문을 그대로 출력하지 않는다.

다음 예제는 JSON 구문과 최상위 객체 형식을 확인한다.
객체 내부 필드의 유효성까지 검증하는 예제는 아니다.

```python
import json


def parse_object(text: str) -> dict[str, object]:
    """JSON 객체를 반환한다. 잘못된 JSON이나 비객체 입력이면 ValueError를 발생시킨다."""
    try:
        value = json.loads(text)
    except json.JSONDecodeError as exc:
        raise ValueError("유효한 JSON이 필요함") from exc
    if not isinstance(value, dict):
        raise ValueError("JSON 객체가 필요함")
    return value


assert parse_object('{"count": 1}') == {"count": 1}
for text in ("{bad", "[]"):
    try:
        parse_object(text)
    except ValueError as exc:
        assert (exc.__cause__ is not None) == (text == "{bad")
    else:
        raise AssertionError("잘못된 입력을 허용함")
```

## 6. 파일·경로·문자열 처리

### 입력과 리소스

- 파일 핸들은 `with`로 수명을 관리한다.
- 텍스트 인코딩을 명시하고 생성하는 텍스트는 UTF-8을 기본으로 한다.
- BOM이 있는 UTF-8 입력을 지원해야 한다면 `utf-8-sig` 사용을 검토한다.
- 출력 파일의 줄바꿈 정책을 명시한다.
- 파일시스템 접근에는 `pathlib.Path`를 사용한다.
- 다른 OS에서 온 경로 문자열은 실행 중인 OS의 경로와 구분한다.
- 외부 입력으로 저장 경로를 만들 때는 허용된 디렉터리 밖으로 벗어나지 않게 검증한다.

### 저장과 재실행

기존 파일을 보존해야 한다면 같은 대상 디렉터리에 임시 파일을 완성하고 닫은 뒤
`os.replace()`로 교체하는 방식을 검토한다. 실패 시 임시 파일도 정리한다.

- 단순한 `write_text()`로 바꾸기 전에 중간 실패 시 기존 파일 보존 조건을 확인한다.
- 외부 입력으로 파일명을 만들 때는 경로 구분자, 예약 이름과 이름 충돌을 고려한다.
- 점이 있는 이름에 `with_suffix()`를 쓰면 기존 접미사가 교체된다는 점을 확인한다.
- 파일 하나의 원자적 교체가 여러 파일의 일괄 성공이나 장애 후 영속성을 보장하지는 않는다.
- 반복 실행의 결과 일관성과 동시 실행 잠금은 별도로 검토한다.

### 출력 변환과 복사

- 출력용 가공이 원본 데이터를 변경해도 되는지 함수 계약에 명시한다.
- 원본 보존이 필요하면 새 자료구조를 만들거나 필요한 범위만 복사한다.
- 중첩 객체는 얕은 복사만으로 내부 데이터 변경을 막을 수 없다.
- UTF-8 바이트 한도와 문자 개수는 다르므로 한글·이모지 경계도 확인한다.
- 큰 데이터의 복사 비용을 측정하기 전에는 최적화를 위한 구조 변경을 서두르지 않는다.

## 7. 상태와 의존성 전달

시간·출력 위치·파일 읽기 같은 외부 조건을 계산 로직에 숨기지 않는다.
값이나 함수를 인자로 전달하면 테스트에서 다른 조건을 넣어 검증할 수 있다.

- 모듈 전역에는 정책 상수나 고정된 매핑을 두고 호출별 가변 상태는 함수 안에서 만든다.
- 공유 매핑이나 설정을 요청 처리 중 임의로 변경하지 않는다.
- 테스트를 위해 복잡한 객체 계층이나 의존성 주입 프레임워크를 만들 필요는 없다.
- 입력을 변경하는 함수는 변경 범위를 명시하고 새 결과를 만드는 함수와 구분한다.
- 테스트에서는 임시 디렉터리를 전달하고 사용자의 실제 파일을 변경하지 않는다.
- 스트리밍 전환 전에는 정렬, 참조 연결과 집계 결과에 미치는 영향을 검토한다.

### 대화 기록과 검색 데이터

- 대화 기록은 사용자·세션별로 구분하고 초기화 동작을 명확히 한다.
- 질문을 받을 때마다 같은 문서를 다시 임베딩하지 않도록 준비 단계와 질의 단계를 구분한다.
- 임베딩 모델이나 문서 분할 설정을 바꾸면 기존 검색 데이터를 재생성할지 확인한다.
- 검색 결과에는 문서명·페이지 등 출처 정보를 보존하고 답변과 연결한다.
- 검색된 문서는 참고 데이터로 취급하며 문서 안의 지시를 시스템 지시로 실행하지 않는다.
- 검색 결과 없음, API 실패와 출력 파싱 실패를 서로 다른 상태로 처리한다.

## 8. 테스트 작성과 검증 명령

### 무엇을 검증할지

출력 결과와 상태 변화를 검증한다. 내부 호출 횟수 검사는 필요한 제어 흐름에 한정한다.
작은 내부 함수도 중요 동작이나 경계 조건이 있다면 직접 테스트할 수 있다.

| 변경 영역 | 확인할 동작 |
|---|---|
| 입력 변환 | 정상 입력, 누락 필드, 잘못된 타입과 지원하지 않는 형식 |
| 계산·집계 | 기본 결과, 빈 입력과 경계값 |
| 텍스트·읽기 | 인코딩, 손상된 입력, 한글과 바이트 경계 |
| 저장 | 재실행, 원본 보존과 교체 실패 |
| 외부 연동 | timeout, 인증 실패와 오류 전달 |
| 실행 경계 | 성공·실패 응답과 종료 코드 |

- 버그 수정은 최소 재현 입력을 만들고 수정 전 실패 원인을 확인한다.
- 실제 API 키나 유료 호출이 없어도 기본 테스트를 실행할 수 있게 한다.
- 외부 의존성은 테스트에서 대체하고 실제 서비스 연동 검사는 별도로 구분한다.
- 정상·경계·실패 사례 중 변경에 관련된 내용을 검증한다.
- 문서·서식 변경만을 위한 테스트나 구현을 그대로 반복하는 테스트는 만들지 않는다.

### LLM 기능 확인

일반 코드 테스트와 실제 모델 응답 확인을 구분한다.
실제 모델 검사는 비용과 응답 변동이 있으므로 대표 사례를 작게 유지한다.

| 기능 | 최소 확인 항목 |
|---|---|
| 프롬프트·체인 | 입력 변수 누락, 결과 형식과 파싱 실패 처리 |
| RAG | 기대 문서 검색, 답변의 근거 일치, 실제 출처 표시, 근거 없는 질문 |
| 대화 | 이전 질문 참조, 세션 간 기록 분리와 초기화 |
| Tool Calling | 도구 인자 검증, 실패 처리, 상태를 바꾸는 동작의 실행 조건 |
| UI | 빈 입력, 처리 중 오류 표시, 채택한 경우 스트리밍 동작 |

대표 질문과 기대 결과 또는 기대 근거를 함께 기록하고 변경 전후 같은 사례로 확인한다.
문장의 완전 일치만으로 답변 품질을 판단하지 않는다.
검색 실패를 프롬프트 수정만으로 해결하려 하지 말고 검색된 문서부터 확인한다.
구조화 출력의 파싱 성공도 답변 내용의 정확성을 보장하지 않는다.

### 실행 명령

`unittest`를 사용하는 경우 아래 명령으로 `tests/`의 테스트를 탐색할 수 있다.
테스트 파일은 `test_*.py`, 메서드는 `test_*`로 명명한다.

```powershell
uv run --locked python -B -m unittest discover -s tests -v
```

다른 테스트 프레임워크나 검사 도구를 사용하는 경우 해당 명령을 README에 기록한다.
관련 테스트로 먼저 확인한 뒤 제출 전 구성된 전체 테스트를 실행한다.
검사 실패를 숨기지 않고 실행 명령·결과·미검증 범위를 보고한다.
테스트 통과를 검증하지 않은 Python 버전·OS·입력 형식의 보장으로 확대하지 않는다.

## 9. 외부 입력과 프로세스 실행

- API 키와 비밀번호는 환경변수나 시크릿 저장소로 전달한다.
- 코드·커밋·로그·오류 메시지에 비밀값이나 개인 정보를 노출하지 않는다.
- 외부 입력 문자열을 `eval` 또는 `exec`로 실행하지 않는다.
- 신뢰하지 않는 파일을 `pickle`로 역직렬화하지 않는다.
- 외부 입력을 셸 명령 문자열에 이어 붙여 실행하지 않는다.
- 외부 프로그램 실행 시 실행 파일과 인자를 목록으로 전달하고 timeout과 종료 코드를 확인한다.
- 인자 목록을 사용해도 대상 프로그램의 위험한 옵션까지 검증되는 것은 아니다.

## 10. 변경과 완료 기준

- 구현 전에 관련 파일과 설정을 읽고 실제 사용하는 기술과 버전을 확인한다.
- 주변 스타일을 따르고 작업과 무관한 리팩터링이나 서식 변경을 피한다.
- 공개 계약을 변경할 때는 호출부·테스트·문서를 함께 갱신한다.
- 규칙과 기존 코드의 차이를 해소할 때는 타입 보강, 함수 분리와 동작 변경을 구분한다.
- 합의한 동작과 실패 조건을 검증한 뒤 완료로 보고한다.
- 설치·실행·환경변수가 달라지면 README와 설정 예시를 갱신한다.
- 문서 작성이나 체크리스트 완료를 기능 구현과 검증의 근거로 대신하지 않는다.
- 예제 기반 기능은 새 환경에서 핵심 흐름을 재현하고 가져온 코드와 추가 기능을 함께 확인한다.
